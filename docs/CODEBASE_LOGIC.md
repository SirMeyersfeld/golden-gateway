# Codebase Logic Documentation

This document explains how the app works from startup to page behavior.

## Tech stack

- **Frontend:** React 18 + TypeScript + Vite
- **Routing:** `react-router-dom`
- **Async/server state:** `@tanstack/react-query`
- **Auth + DB:** Supabase (`@supabase/supabase-js`)
- **Forms:** `react-hook-form` + `zod` (used in admin deal form)
- **UI:** Tailwind + shadcn/Radix components + custom CSS utilities
- **Animations/charts:** Framer Motion + Recharts

## Runtime flow (app startup)

1. `src/main.tsx` renders `<App />`.
2. `src/App.tsx` wraps app with:
   - `QueryClientProvider`
   - Tooltip + toast providers
   - `BrowserRouter`
   - `AuthProvider`
3. Routes are declared in `App.tsx`:
   - Public: `/auth`, `/reset-password`
   - Protected: everything else via `ProtectedRoute`

## Route architecture

Inside protected routes, `Layout` wraps all app pages:

- Investor/general:
  - `/` → `Index`
  - `/deals` → `Deals`
  - `/portfolio` → `Portfolio`
  - `/documents` → `Documents`
  - `/invest` → `InvestWizard`
- Fund manager/admin:
  - `/admin`
  - `/admin/deals`
  - `/admin/deals/new`
  - `/admin/deals/:id/edit`
  - `/admin/investors`
  - `/admin/capital-calls`
  - `/admin/studio`

`/admin` pages are not explicitly role-gated at route level; access control relies on DB policies and UI nav visibility.

## Authentication and roles

File: `src/contexts/AuthContext.tsx`

What it stores:

- `session`
- `user`
- `role` (`investor` or `fund_manager`)
- `loading`

What it provides:

- `signUp`, `signIn`, `signOut`
- `resetPassword`, `updatePassword`

How role is loaded:

- On auth change and on initial session fetch, it queries `user_roles` by `user_id`.

Role assignment on signup:

- The signup call writes role/full name into user metadata.
- A DB trigger creates `profiles` and `user_roles` rows from metadata.

## Protected route behavior

File: `src/components/ProtectedRoute.tsx`

- Shows spinner while auth state is loading.
- Redirects to `/auth` if no session.
- Otherwise renders child routes.

## Navigation shell logic

File: `src/components/Layout.tsx`

- Renders fixed top nav + mobile nav.
- Computes active route by current pathname.
- Shows admin nav item only when role is `fund_manager`.
- Shows user email and role badge.
- Handles sign-out via `useAuth().signOut`.

## Data access pattern

Most pages follow this pattern:

1. Fetch data with `useQuery`.
2. Transform/filter in component (`useMemo` where needed).
3. Mutations with `useMutation`.
4. `queryClient.invalidateQueries(...)` after writes.

This is the standard pattern to keep UI fresh.

## Investor-side page logic

## `Index` (landing/overview)

- Uses `cms_blocks` (`landing_hero`, `landing_stats`) if available.
- Falls back to local default text/stats if CMS data is missing.
- Primarily presentational + trust/CTA content.

## `Deals`

- Fetches all deals from `deals` table.
- Client-side:
  - Search by name/sector/stage
  - Filter by sector and status
  - Sort by date/target/raised
- Open deals show “Invest via SPV” action linking to `/invest`.

## `InvestWizard`

5-step flow:

1. Select deal (open deals only)
2. Enter amount (must be >= minimum)
3. Accept terms checkbox
4. Sign all required docs (simulated toggles)
5. Confirm and submit

Submit behavior:

- Inserts into `investments` table with status `committed`.
- Invalidates `open-deals` query.
- Shows success state.

Important caveat:

- `preselectedDeal` is read from query param `deal`, but code compares it to `deal.id` in one place. If URL passes deal name instead of ID, auto-select can fail.

## `Portfolio`

- Uses local static arrays for summary/chart/holdings (currently mock UI data).
- Not yet wired to live Supabase portfolio calculations.

## `Documents`

- Uses static local document list (mock data).
- Actions (view/download) are UI-only at the moment.

## Admin-side page logic

## `AdminDashboard`

- Fetches deals created by current manager (`created_by = user.id`).
- Fetches related investments and capital calls by those deal IDs.
- Computes summary metrics in UI.
- Uses static chart data for trend visualization.

## `ManageDeals`

- Lists manager-owned deals.
- Delete mutation removes selected deal.
- Edit navigates to deal form.

## `DealForm`

- Uses `react-hook-form` + Zod schema validation.
- Create mode inserts row in `deals`.
- Edit mode loads by `id` and updates row.
- Always sets `created_by` to current user.

## `Investors` (admin)

- Gets manager deals.
- Loads investments where `deal_id IN manager_deal_ids`.
- Displays investor id, deal, amount, status, date.

## `CapitalCalls` (admin)

- Gets manager deals.
- Lists calls for those deals.
- Can create call and update status (`pending`/`paid`/`overdue`).
- `call_number` is generated by counting existing calls for selected deal.

## `Studio` (admin CMS)

- Reads/writes `cms_blocks`.
- If table is missing, shows setup guidance in UI.
- Edits title/body/json data and upserts by `key`.

## Supabase schema and security

Defined in migrations:

- `supabase/migrations/20260223184433_...sql`
- `supabase/migrations/20260224045341_...sql`

Core objects:

- Enum: `app_role` (`investor`, `fund_manager`)
- Tables:
  - `profiles`
  - `user_roles`
  - `deals`
  - `investments`
  - `capital_calls`
- Function: `has_role(user_id, role)` (security definer)
- Triggers:
  - auto profile/role creation after signup
  - auto `updated_at` on updates

RLS highlights:

- Authenticated users can view deals.
- Fund managers can CRUD only their own deals.
- Investors can create/view only their own investments.
- Fund managers can view investments in their own deals.
- Fund managers can manage capital calls for their own deals.
- Investors can view capital calls only for deals they invested in.

## Type safety and generated DB types

File: `src/integrations/supabase/types.ts`

- Contains generated `Database` type for table rows/insert/update.
- Supabase client is created with this type, enabling typed queries.

## Known architectural gaps (for roadmap)

1. Some pages are still mock-driven (`Portfolio`, `Documents`, dashboard chart).
2. Admin route access is not route-guarded by role in frontend.
3. CMS table required by `Studio` is not created in current migrations.
4. Query keys are mostly ad-hoc strings; can be centralized later.
